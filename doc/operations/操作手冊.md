## 3. 告警機制操作

### 3.1 告警觸發條件

目前設定的告警規則分為**四個群組**（業務 / 管線健康 / LLM 預算 / 設備分類安全；noData/execErr 策略對照見 §3.5）：

**Group 1：業務告警（EMS-功率告警）**

| 規則名稱 | UID | 條件 | 持續時間 | 通知方式 |
|---------|-----|------|---------|---------|
| 功率超限 | `ems-power-kw-high` | power_kw 平均 > 100 kW | 30 秒 | Telegram |

**Group 2：管線健康告警（EMS-管線健康）**

| 規則名稱 | UID | 條件 | 持續時間 | 通知方式 |
|---------|-----|------|---------|---------|
| 電表資料寫入停滯 | `ems-pipeline-electricity-stale` | 過去 2 分鐘 `electricity_measurements` 0 筆 | 1 分鐘 | Telegram (critical) |
| 工廠資料寫入停滯 | `ems-pipeline-factory-stale` | 過去 2 分鐘 `factory_measurements` 0 筆 | 1 分鐘 | Telegram (critical) |

**Group 3：LLM 預算告警（EMS-預算告警，PRD-0004 FR-400~405）**

| 規則名稱 | UID | 條件 | 持續時間 | 通知方式 |
|---------|-----|------|---------|---------|
| L1 預算 80% | `ems-l1-budget-warn` | L1（非 guardrail）當期 `cost_usd/budget_usd ∈ [0.8,1.0)` | 5 分鐘 | Telegram (warning) |
| L1 預算 100% | `ems-l1-budget-exhausted` | L1 `≥ 1.0`（fail-closed 降級 system_fallback）| 即時 | Telegram (critical) |
| guardrail 80% | `ems-guardrail-budget-warn` | guardrail 當期 `[0.8,1.0)` | 5 分鐘 | Telegram (warning) |
| guardrail 100% | `ems-guardrail-budget-exhausted` | guardrail `≥ 1.0`（連 L1 一起停走 fallback）| 即時 | Telegram (critical) |

> 預算告警的處置與「收到後查是哪個 provider / 幾 %」見 **§3.7**。`noDataState=OK`（月初無 ledger row 不誤觸）/ `execErrState=Error`（查詢壞了會出聲）。
> （另有 Group 4「EMS-設備分類安全」FR-339/344：guardrail BLOCK 爆量 / 大量 deactivate，處置見 PRD-0003 稽核章節。）

### 3.2 手動觸發告警（測試用）

**方法 A：調高模擬功率（測試業務告警）**

```bash
# 將基礎電流調高到 200A，功率會超過 100kW
python3 scripts/simulator_control.py --username demo set sim-001 current_base_a=200 --reason "維運測試"

# 等待 30-90 秒後，Telegram 會收到告警
# 查看告警狀態
curl -s -u admin:admin http://localhost:3000/api/prometheus/grafana/api/v1/rules | jq '.data.groups[].rules[] | {name, state}'
```

**方法 B：注入故障模式**

```bash
# 凍結數值（仍回應通訊）
python3 scripts/simulator_control.py --username demo set sim-001 fault_mode=freeze --reason "維運測試"

# 數值歸零（模擬電表故障）
python3 scripts/simulator_control.py --username demo set sim-001 fault_mode=zero --reason "維運測試"

# 恢復正常
python3 scripts/simulator_control.py --username demo set sim-001 fault_mode=none --reason "維運測試"
```

**方法 C：停 ingest 服務（測試管線健康告警）**

```bash
# 停電表 ingest → 2~3 分鐘後 Telegram 收到「電表資料寫入停滯」
docker compose stop ingest

# 停 KC ingest → 2~3 分鐘後 Telegram 收到「工廠資料寫入停滯」
docker compose stop kc-ingest

# 復原（1 分鐘內告警自動解除，會收到 RESOLVED 通知）
docker compose start ingest kc-ingest
```

> 管線告警的 `noDataState/execErrState` 都設為 `Alerting`（沒資料 = 真的壞了）。
> 業務告警則設為 `OK`（避免管線中斷時誤觸功率告警）。設計理由見 §3.6。

### 3.3 恢復正常狀態

```bash
# 恢復正常功率參數
python3 scripts/simulator_control.py --username demo set sim-001 current_base_a=100 current_swing_a=40 --reason "維運測試"

# 確認故障模式已關閉
python3 scripts/simulator_control.py --username demo set sim-001 fault_mode=none --reason "維運測試"
```

### 3.5 四類告警的 noData/execErr 策略（設計分工）

各組告警的 `noDataState` / `execErrState` 設定刻意不同，因為它們監控的是不同層次：

| 告警分組 | 監控對象 | noDataState | execErrState | 為什麼 |
|---------|---------|-------------|--------------|-------|
| 業務告警（功率超限） | 業務指標（kW） | **OK** | **OK** | 沒資料/SQL 錯時不該告警，否則改 schema 或停 ingest 都會誤觸 |
| 管線健康（寫入停滯） | 基礎設施（資料流） | **Alerting** | **Alerting** | 沒資料就是真的壞了 — 這正是這組告警要抓的 |
| **LLM 預算（Group 3）** | 成本比例（ledger）| **OK** | **Error** | 月初無 ledger row = 0% 不該誤觸（OK）；但查詢壞了要出聲（Error），避免成本守衛靜默失效 |
| **設備分類安全（Group 4）** | 稽核事件（audit）| **OK** | **Error** | 平靜期無 audit row 不該誤觸（OK）；壞查詢要出聲（Error），避免安全告警靜默失效 |

> 三種策略的差異本質：**業務**＝沒資料就當沒事（OK/OK）；**管線**＝沒資料就是壞（Alerting/Alerting）；**預算 / 安全**＝沒資料當沒事、但「查詢本身壞掉」要出聲（OK/Error）——因為它們是守衛性告警，寧可知道偵測器壞了。

**為什麼分開**：以前業務告警吃下「沒資料」的責任，結果一改 schema 或一停 ingest 就誤觸 Telegram。把兩種職責拆開後：

- 改業務閾值（如 100 → 120 kW）只動業務告警
- 改 DB schema / 停服務除錯時，只有管線告警會出聲，且這正是預期行為
- 收到「管線停滯」通知 → 看 §1.2 資料流圖，依鏈路順序排查容器

### 3.7 收到 LLM 預算告警後的處置 SOP（PRD-0004 FR-400~405）

> **為什麼 Telegram 訊息沒寫是哪個 provider / 幾 %**：預算告警為**低基數**設計（FR-403），SQL 只回「跨閾值的 provider 數」單一 scalar，**provider 名稱與金額不進 Grafana label**（避免 series 爆量）。因此收到告警後須回 DB 查明細。

**Step 1 — 查是哪個 provider、花了多少、幾 %**

```bash
docker exec ems-timescaledb psql -U postgres -d ems -c "
SELECT provider, cost_usd, budget_usd,
       round(cost_usd / NULLIF(budget_usd,0) * 100) AS pct,
       period_start::date, period_end::date
FROM public.llm_budget_ledger
WHERE period_start <= now() AND period_end > now()   -- 當期 row
ORDER BY pct DESC;"
```

- `provider = 'guardrail'` → L2 守衛預算（達 100% 依 FR-340 **連 L1 一起停**走 system_fallback）。
- 其他（如 `openai`）→ L1 分類預算（達 100% → 分類 fail-closed 降級 system_fallback）。
- `pct ≥ 100` → 該層已停用、改回退值；`80 ≤ pct < 100` → 仍運作，提前預警。

**Step 2 — 處置（依當下取捨）**

| 手段 | 做法 | 效果 | 備註 |
|------|------|------|------|
| **切 mock（最快、零成本、立即止血）** | 設 `LLM_PROVIDER=mock`（或 `GUARDRAIL_PROVIDER=mock`）於 `.env` → `docker compose up -d device-service device-service-mcp` | 分類改走 deterministic mock，不再產生 LLM 成本；告警隨 cost 不再增長而緩解 | 分類品質降為 mock 等級，屬暫時止血 |
| **提高當期預算** | ⚠️ **目前無 API**：FR-334 `/admin/budget/extend` 在 PRD-0003 有規格但**尚未實作**。暫以 OPS/superuser 手動 SQL 調高當期 row 的 `budget_usd`（見下）| 比例分母變大 → 告警解除、AI 分類續行 | **臨時手段**；正式上線前應補 FR-334 端點（帶 audit / rate-limit），不應長期靠手動 SQL |
| **等下一期** | 不動作，等 `period_end` 翻新期 | 新期 row 以 env `*_MONTHLY_BUDGET_USD` 重新起算 | 期間 AI 分類維持 fallback |

**臨時調高當期預算（FR-334 未實作前的 workaround，OPS only）**

```bash
# 例：把當期 openai 預算從 20 調到 40（謹慎；此操作未經 audit log，屬臨時手段）
docker exec ems-timescaledb psql -U postgres -d ems -c "
UPDATE public.llm_budget_ledger
SET budget_usd = 40.0, updated_at = now()
WHERE provider = 'openai' AND period_start <= now() AND period_end > now();"
```

> 註：`budget_usd` 一旦該期 row 建立即固定（`get_period_budget` 回現有 row 值），改 env `LLM_MONTHLY_BUDGET_USD` **只影響尚未建立 row 的新期**，不會回頭改當期 → 故當期調額目前只能手動 SQL 或待 FR-334。

**Step 3 — 確認告警解除**

```bash
# 切 mock 或調額後，rule 會在下個 eval interval（≤1 分鐘）回 inactive
curl -s -u admin:admin http://localhost:3000/api/prometheus/grafana/api/v1/rules \
  | jq '.data.groups[] | select(.name=="EMS-預算告警") | .rules[] | {name, state}'
```

## 4. API 操作指南

### 4.1 Simulator 統一控制 API（BFF 端口 8003）

本機 OPS 帳號為 `demo`；CLI 每次互動輸入密碼，並自動取得 state 的 instance/revision。完整指令從專案根目錄執行。
需要短指令 `sim list` 時，先依 [sim 簡寫設定](simulator-control.md#3-建立-sim-簡寫) 建立 function；`sim` 不是預裝命令。

```bash
python3 scripts/simulator_control.py --username demo list
python3 scripts/simulator_control.py --username demo state sim-001
python3 scripts/simulator_control.py --username demo set sim-001 current_base_a=150 --reason "電流調整測試"
python3 scripts/simulator_control.py --username demo set sim-001 fault_mode=freeze --reason "凍結量測測試"
python3 scripts/simulator_control.py --username demo set sim-001 fault_mode=none --reason "恢復量測"
python3 scripts/simulator_control.py --username demo history --limit 20
```

電表、PLC、MQTT sensor、Delta 共用 `/api/simulators` 入口；命令需 OPS session 與允許的 Origin。
每次操作保留操作者、時間、理由、前後設定、結果及 UUID。逾時結果可能是 `outcome_unknown`，先查詢或對帳，不能自動重送。
`freeze` 讓量測停止變動，但仍回應通訊；`zero` 歸零即時量測並保留累計電量。
舊 host :8001 API 已撤下，原生 meter POST 回 410；Modbus/MCP 僅保留讀取。

完整設定範圍、其他三台的操作、HTTP 契約、對帳及備份見 [Simulator 統一控制與操作紀錄](simulator-control.md)；驗收見 [驗收紀錄](simulator-control-verification.md)。

### 4.2 Query API - PostgREST (端口 3001)

#### 查詢最新資料

```bash
# 電表最新 10 筆
curl "http://localhost:3001/electricity_measurements?order=time.desc&limit=10"

# 電表最新 1 筆
curl "http://localhost:3001/electricity_measurements?order=time.desc&limit=1"

# 工廠最新 5 筆（PLC + JSON sensor）
curl "http://localhost:3001/factory_measurements?order=time.desc&limit=5"
```

#### 依設備 ID 查詢

```bash
# 電表
curl "http://localhost:3001/electricity_measurements?device_id=eq.sim-001&order=time.desc&limit=10"

# KC 工廠 PLC
curl "http://localhost:3001/factory_measurements?device_id=eq.plc-001&order=time.desc&limit=10"

# KC JSON sensor
curl "http://localhost:3001/factory_measurements?device_id=eq.sensor-001&order=time.desc&limit=10"
```

#### 時間範圍查詢

```bash
# 過去 1 小時
curl "http://localhost:3001/electricity_measurements?time=gte.$(date -u -d '1 hour ago' +%Y-%m-%dT%H:%M:%S)&order=time.desc"

# 指定時間範圍
curl "http://localhost:3001/electricity_measurements?time=gte.2026-04-23T00:00:00&time=lte.2026-04-23T23:59:59&order=time.desc"
```

#### 只選特定欄位

```bash
curl "http://localhost:3001/electricity_measurements?select=time,power_kw,voltage&order=time.desc&limit=10"
```

#### 條件過濾

```bash
# 功率大於 50 kW
curl "http://localhost:3001/electricity_measurements?power_kw=gt.50&order=time.desc&limit=10"

# 功率介於 50~100 kW
curl "http://localhost:3001/electricity_measurements?power_kw=gte.50&power_kw=lte.100&order=time.desc"

# 工廠溫度大於 28 C
curl "http://localhost:3001/factory_measurements?temperature=gt.28&order=time.desc&limit=10"

# 工廠 PLC 壓力資料
curl "http://localhost:3001/factory_measurements?device_id=eq.plc-001&pressure=not.is.null&order=time.desc&limit=10"
```

-- 最新 5 筆資料
SELECT time, device_id, voltage, current, power_kw 
FROM electricity_measurements 
ORDER BY time DESC 
LIMIT 5;

LIMIT 10;

### 4.7 Device Service 操作 (REST 8002 + MCP 127.0.0.1:8766)

`ems-device-service`（PRD-0003）負責設備註冊與 AI 自動分類，採雙 DB pool 最小權限
（AI pool 不可讀原始遙測/corrections 內容；OPS pool 才有完整權限）。`ems-device-service-mcp`
是同映像的 MCP 端，只開 AI 通道三工具。

```bash
# REST 健康檢查（雙 pool 狀態）
curl -s http://localhost:8002/healthz

# MCP 健康檢查（免認證 liveness，供 healthcheck 用）
curl -s http://localhost:8766/healthz        # {"status":"ok"}

# MCP 工具呼叫一定要帶 AI 通道金鑰，否則 401
curl -i -X POST http://127.0.0.1:8766/mcp \
  -H "X-API-Key: $AI_API_KEY" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  --data '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

**三通道金鑰**（`.env`，缺值該通道 fail-closed）：`OPS_API_KEY`（人工 lifecycle/feedback）、
`INGEST_API_KEY`（遙測來源）、`AI_API_KEY`（分類 + MCP）。REST API 規格見 `api/openapi.yml`
（tag: Device Service）。

> ⚠️ **AI 金鑰輪替需重啟 MCP 容器（L-3）**：MCP server 在啟動時讀一次 `AI_API_KEY`，
> 改了 `.env` 後舊金鑰仍有效，必須 `docker compose up -d device-service-mcp` 才會生效。
>
> ⚠️ **Rate-limit 是「單一 AI client」假設（M-2）**：MCP 的每 IP 60/min 限制，在 docker-proxy
> host 映射下所有呼叫端共用 bridge gateway IP，因此實質上是「全域 60/min」。目前部署只有一個
> AI client，可接受；若日後要多 client，需走 ADR 改成 per-key/可信代理 X-Forwarded-For。
>
> 安全：MCP 端只綁 `127.0.0.1:8766`、X-API-Key 為唯一閘門、未預期例外只回 `internal error`
> 不洩漏內部細節；每次工具呼叫都寫結構化 audit log（tool/caller_ip/device/status/latency）。

```bash
# 重啟 / 套用金鑰輪替
docker compose up -d device-service device-service-mcp
# 看 MCP audit log
docker compose logs -f device-service-mcp | grep mcp_tool_call
```

## 5. 修改警示訊息

### 5.1 修改告警規則

編輯檔案：`infra/grafana/provisioning/alerting/rules.yaml`

檔案結構（兩個 group，職責分離見 §3.5）：

```yaml
groups:
  # Group 1: 業務告警（noData/execErr → OK，避免管線中斷誤觸）
  - orgId: 1
    name: EMS-功率告警
    folder: EMS
    interval: 1m
    rules:
      - uid: ems-power-kw-high
        title: "功率超限 (power_kw > 100 kW)"
        for: 30s
        labels:
          severity: warning
        annotations:
          summary: "功率超過 100 kW"
          description: "過去 5 分鐘平均 power_kw 超過 100 kW，請確認現場狀況"
        noDataState: OK         # 沒資料 → 視為正常
        execErrState: OK        # SQL 錯 → 視為正常

  # Group 2: 管線健康告警（noData/execErr → Alerting，沒資料就是真的壞了）
  - orgId: 1
    name: EMS-管線健康
    folder: EMS
    interval: 1m
    rules:
      - uid: ems-pipeline-electricity-stale
        title: "電表資料寫入停滯 (>2 分鐘無新資料)"
        # 條件：COUNT(*) of electricity_measurements where time > now()-2m < 1
        for: 1m
        labels:
          severity: critical
          component: pipeline
        noDataState: Alerting   # 沒資料 = 壞了
        execErrState: Alerting  # SQL 錯 = 壞了
      - uid: ems-pipeline-factory-stale
        # 同上，但查 factory_measurements
```

**修改業務告警閾值：** 找到 `ems-power-kw-high` 規則內的 `params: - 100`，改成你要的數值（例如 120）

**修改管線停滯時間窗：** 找到 SQL 中的 `interval '2 minutes'`，改成你要的時間（要同時調整 `for:` 持續時間）

**修改後重新載入：**

```bash
curl -u admin:admin -X POST http://localhost:3000/api/admin/provisioning/alerting/reload
```

> 若改動的是 group 結構或 rule body（非單純標籤/註記），reload API 有時 fingerprint 偵測不到，需要 `docker compose restart grafana` 才會生效。詳見 §7.7。

### 5.4 新增告警規則

在 `rules.yaml` 的 `rules:` 下新增：

```yaml
      - uid: ems-voltage-low
        title: "電壓過低 (voltage < 360V)"
        condition: C
        data:
          - refId: A
            relativeTimeRange:
              from: 300
              to: 0
            datasourceUid: timescaledb-ems
            model:
              rawQuery: true
              rawSql: |
                SELECT time, voltage
                FROM electricity_measurements
                WHERE time >= now() - interval '5 minutes'
                ORDER BY time
              refId: A
          - refId: B
            datasourceUid: "-100"
            model:
              type: reduce
              expression: A
              reducer: mean
          - refId: C
            datasourceUid: "-100"
            model:
              type: threshold
              expression: B
              conditions:
                - evaluator:
                    type: lt        # lt = less than
                    params:
                      - 360
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "電壓過低警告"
          description: "過去 5 分鐘平均電壓低於 360V，可能有電力品質問題"
        notification_settings:
          receiver: Telegram
```

## 7. 故障排除

### 7.1 告警沒有觸發

1. **檢查功率是否真的超過閾值**
   ```bash
   docker exec ems-timescaledb psql -U postgres -d ems -c \
     "SELECT AVG(power_kw) FROM electricity_measurements WHERE time > NOW() - INTERVAL '5 minutes';"
   ```

2. **檢查告警規則狀態**
   ```bash
   curl -s -u admin:admin http://localhost:3000/api/prometheus/grafana/api/v1/rules | jq
   ```

3. **檢查 Grafana 日誌**
   ```bash
   docker compose logs grafana | grep -i alert
   ```

### 7.2 Telegram 收不到通知

1. **確認 Bot Token 正確**
   ```bash
   cat .env | grep TELEGRAM
   ```

2. **確認 Chat ID 正確**
   ```bash
   cat infra/grafana/provisioning/alerting/contact-points.yaml | grep chatid
   ```

3. **測試 Bot 是否能發訊息**
   ```bash
   curl -X POST "https://api.telegram.org/bot<YOUR_TOKEN>/sendMessage" \
     -d "chat_id=7171144544" \
     -d "text=測試訊息"
   ```

### 7.3 API 回應空陣列

1. **確認資料庫有資料**
   ```bash
   docker exec ems-timescaledb psql -U postgres -d ems -c \
     "SELECT COUNT(*) FROM electricity_measurements;"
   ```

2. **確認 api schema view 存在**
   ```bash
   docker exec ems-timescaledb psql -U postgres -d ems -c "\dv api.*"
   ```

3. **重啟 PostgREST**
   ```bash
   docker compose restart query
   ```

### 7.4 KC 工廠資料沒有出現在 Grafana

1. **確認 DB 有 factory 資料**
   ```bash
   docker exec ems-timescaledb psql -U postgres -d ems -c      "SELECT device_id, device_type, COUNT(*) FROM factory_measurements WHERE time > NOW() - INTERVAL '10 minutes' GROUP BY device_id, device_type;"
   ```

2. **確認 KC ingest 沒有寫入錯誤**
   ```bash
   docker compose logs --tail=80 kc-ingest
   ```

3. **重新載入 Grafana dashboard provisioning**
   ```bash
   curl -u admin:admin -X POST http://localhost:3000/api/admin/provisioning/dashboards/reload
   ```

4. **瀏覽器硬重新整理**
   ```text
   http://localhost:3000/d/ems-overview
   ```

### 7.5 MCP Inspector 連不上

1. **確認 endpoint 不是用 Chrome 直接打開**：MCP endpoint 需要 MCP client。
2. **Inspector 設定**：Transport 選 `Streamable HTTP`，URL 填 `http://localhost:8765/mcp`。
3. **確認容器在跑**：
   ```bash
   docker compose ps kc-mcp-server
   docker compose logs --tail=80 kc-mcp-server
   ```
4. **如果看到 `Not Acceptable`**：client 沒送 `Accept: application/json, text/event-stream`。

### 7.6 容器一直重啟

```bash
# 查看錯誤訊息
docker compose logs --tail=50 <container_name>

# 常見原因：
# - 密碼不一致 → 檢查 .env
# - 相依服務未啟動 → 檢查 depends_on 的服務
# - 設定檔語法錯誤 → 檢查 YAML/conf 檔案
```

### 展位 QR Code 綁定訪客示範告警（PRD-0024 / ADR-036）
**展位流程**
1. 展位螢幕開啟 EMS → 警報中心並以 OPS 帳號（demo）登入；面板顯示 QR Code、「目前綁定」、「今日已觸發」。session 最長 8 小時，長展期間若出現登入表單請重新登入。

**狀態與排查**（面板 Bot 狀態與 `docker logs ems-bff` 的 `demo_binding state=` 一致）
| 狀態 | 意義 | 處置 |
|---|---|---|
| ready | 正常輪詢 | — |
| starting | 啟動中（數秒） | 稍候 |
| webhook_active | Bot 被設定了 webhook，getUpdates 無法使用 | 先確認誰設定、是否仍需要；系統不會自動刪除 webhook |
| conflict | 另一程式也在 getUpdates（409） | 找出並停止另一消費者（常見：未移除的預備測試容器 `ems-bff-booth-preprod`） |
| unauthorized | Token 無效（401/404），輪詢已停止 | 更新 `.env` 後重啟 bff |
| unavailable | 網路／DNS 失敗（自動退避重試）、狀態檔被鎖或未設定 Telegram | 查容器出站與 volume；固定對象示範仍可用 |
