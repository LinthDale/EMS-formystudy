# 無 Pi 數據採集驗證與驗收基準 v0.1

日期：2026-11-12（Asia/Taipei）。狀態：測試計畫；以下門檻為單設備 Windows 台架的提議驗收基準，不是已達成結果、產業強制標準或現場 SLA。對應 PRD-0020／ADR-031；可靠補送、中央對帳延續 Draft PRD-0021／ADR-030，不能把本計畫當作其已實作證明。

## 1. 目的與測試範圍

先讓每次採集成功、失敗與補送都有可核對的證據，再逐項注入故障。每一關先固定設定，保存結果，通過後才增加下一個故障；失敗保留原證據，修復後另開 run_id 重驗。

```text
同一台 Windows PC
Delta RTU simulator → USB–RS485 #1 COM3 → 實體雙絞線 → USB–RS485 #2 COM4
                                                        ↓
                                           正式 Poller → SQLite → MQTT → EMS DB/API/UI
```

PC 同時代替逆變器與樹莓派。可驗串口、協定解析、排程、暫存、程序故障及 EMS；不能驗 Pi ARM/SD 卡斷電耐受、SIM7600G-H/4G、台達真機倍率/寄存器與現場電磁干擾。相同 PC 的時鐘與電源共因也不能代表獨立站端／中央。

最新唯讀盤點：COM3、COM4 為 OK；未見 delta_device Python 程序。尚未探測串口獨占開啟，不能排除其他種類程序占用。先前完整證據見 [2026-11-12 台架紀錄](../../output/delta-rtu-bench-20261112/README.md)：110/110 採集、15/15 DB/API、5 筆 sender 離線補送、78 項回歸。以下新關卡仍待執行，舊短測不能抵扣長測。

## 2. 資料有效的定義

一筆正常量測必須同時滿足：

1. 來源明確：device_id、串口序號、型號/profile版本、設定版本可追溯。
2. 協定有效：預期站號、功能碼、位址、長度及 CRC 合法；半包、錯站號、錯 CRC 不進正常量測。
3. 語意正確：依獨立 golden vector 核對倍率、字序、單位與欄位。voltage/current 是 L1，power_kw 是三相總有功，energy_kwh 是累計發電；不能混淆今日與累計電量。不能只用同一段 encoder/decoder 互相比對。
4. 時間可信：保留讀取起訖與本機採集時間，UTC 儲存、台灣時間顯示；排程耗時用 monotonic。現行 sampled_ns 在讀取前取得，是採集器時間，並非逆變器內部精準量測時刻。多次 register 讀取不保證真機原子快照。
5. 保存／送達可證明：區分 SQLite commit、broker PUBACK、中央 DB commit、API可見與UI呈現。每層不能替代下一層。
6. 缺值可辨識：正常夜間 0 kW、設備失聯、暫存未送、資料過期分開。不得補 0、複製前值或重新標時間冒充新樣本；故障原因無證據時標 unknown。

Modbus CRC／回應逾時的協定依據：[Modbus Serial Line Guide V1.02](https://www.modbus.org/file/secure/modbusoverserial.pdf)。USB／作業系統等待行為參考 [pySerial API](https://pyserial.readthedocs.io/en/latest/pyserial_api.html)。以下成功率、時間與測試長度為專案台架提議值，不由這兩份文件保證。

## 3. 每一關共用的量測帳本

在測試工具建立獨立 ledger，不更改現行 telemetry schema；不得以既有 API 尚未具備的 sample_id/quality 欄位假裝已實作。未有帳本的關卡狀態只能是「待量測」。

每次 run 保存：run_id、開始/結束 UTC、原始碼 SHA256、Python/套件/驅動版本、轉換器序號、COM、線長、19200/8N1/unit1/base1、timeout、採樣間隔與生效時刻；修改設定另開 run。

每個預定採樣槽保存：slot_id、預定 monotonic 時刻、實際開始/結束、結果、錯誤原因、採集時間、四個量測欄位、SQLite commit結果；送達另記 broker ACK 與首次觀察DB/API的時刻。查詢觀察時間是延遲上界，不冒稱精確 DB commit 時間。原始 RTU hex 僅在有界診斷模式採集，避免長期無限制寫檔。

計算：

- E：依固定起點 t0、間隔 I 及半開區間 [t0,t1) 產生的應採槽數。維護/停機/設定切換需分段，不用有效第一筆到最後一筆倒推分母。
- A：實際啟動的槽數；C：取得完整有效資料的槽數；L：SQLite 已提交樣本；D：中央符合該來源樣本的唯一量測。
- 排程覆蓋率=A/E；讀取成功率=C/A；有效採集率=C/E；入庫完整率=已核對來源樣本數/L。A=0/L=0 報 N/A，不報100%。
- 重試列為同一 slot 的額外 attempt，不能拿多次成功沖高覆蓋率。現行無當輪即時重試；PRD-0021 多設備設計也是當輪不立即重試，不能逕自加無限 retry。
- 計數相同仍不足：本台架用獨立 device_id、原始時間與四欄位逐筆集合比對，另列缺少、額外、重複、內容不符；不得只看 COUNT 或 MAX(time)。正式序號/hash/中央receipts仍是 PRD-0021 待實作。
- 採樣延遲與耗時報 p50/p95/p99/max；記錄連續失敗最大次數、最舊待送年齡、queue峰值與結束值、DB大小、CPU/RAM及磁碟餘量。

建議輸出：manifest.json、slots.jsonl、samples.jsonl、events.jsonl、db-comparison.json、report.md、sha256.json；記錄實際測試步驟與時間，不包含密碼。

故障注入期間預期會有缺測，該段成功率不要求99.9%；要求完整分類、零壞值入庫與符合恢復門檻。正常段與注入段分開報，不能排除自然發生的錯誤來美化成功率。

## 6. 尚缺能力與正式標準界線

現有：CRC/站號/長度檢查、有限總timeout、失敗拒收與下輪讀取、SQLite暫存、MQTT QoS1、既有資料API。現行timeout=3秒是單次交易等待設定，不能當作整個多段poll必定3秒內完成。

待補或另驗：完整slot/attempt帳本、精確錯誤分類與告警、跨重啟序號/身份、中央committed ACK/去重/對帳、受控故障工具、USB改號恢復與UI品質狀態。規劃中的last_good_age等指標不可視為已上線。

上一輪提到的「有限即時重試」只是可選方向，尚未實作；本計畫遵循既有PRD-0021的當輪不立即重試策略。若將來改成有限retry，先核定整輪deadline與多設備排程預算，再改契約及驗收，不能只調大retry次數。

正式場域門檻最後還需要設備數、採樣級距、可接受缺測、最長離線時間及現場線長/供電條件共同核定；本文件先建立可重現、可追溯的單設備台架基準。
