## 1. 執行摘要

大同智能提出的不是單純「PV＋電池＋柴油機」設備清單，而是一套面向防災場域的微電網操作方案。從 24 張資料可以看出，其工作已涵蓋：

- 場域與避難服務需求。
- PV、ESS、DG、ATS、計量與 EMS 硬體配置。
- 市電、ESS、DG 三種電源之間的模式切換。
- ESS GFM／GFL 角色轉換與 SOC 調度。
- 72 小時供電時序與燃油估算。
- 現場 Modbus、乾接點、DNP3 上位通訊與 Web HMI。
- 異常處理、事件記錄、FAT、SAT 與 72 小時實測。

這代表大同智能已經把方案推進到「可討論控制邏輯與驗收項目」的層次，而不是停留在概念簡報。其最明顯的強項是系統整合思維：同一份方案同時處理電力、控制、通訊、操作與測試。

公平的總結是：

> 大同智能的方案骨架完整、現場導向明確、工程準備度高；最值得肯定的是模式設計、72 小時運轉思考、通訊／HMI 規劃與 FAT/SAT 意識。現階段不足主要集中在數值版本不一致、控制責任過度集中於 EMS、狀態轉移 gate 未完整，以及 72 小時能量與保護設計尚未形成可追溯計算。

因此，這份提案很適合作為下一輪 PDR 的基礎，不宜被簡化成「有錯所以不能用」，也不應在未補齊單線圖、設備能力與計算書前直接當成施工定版。

## 2. 場域與大同智能要解決的問題

方案場域是彰化縣大村鄉加錫、貢旗兩村聯合集會所，平時是活動中心，災害時轉為 100 人避難場域及第二備援災害應變中心。

大同智能面對的實際問題包括：

1. 平時由市電供電，但要保留防災電量。
2. 市電中斷後，現場必須切成孤島。
3. ESS 要先承接，低 SOC 時再交給 DG。
4. DG 運轉時不只供負載，也替 ESS 補電。
5. 白天盡量利用 PV，降低柴油耗用。
6. 災時要連續維持 72 小時。
7. 現場設備需要可被監看、控制、記錄與遠端維運。
8. 切換失敗或設備失聯時要有告警與備援行為。

這是一個典型的小型防災微電網題目。大同智能的價值，不在某一個演算法特別複雜，而在把這八個問題放進同一套操作系統中。

## 5. 2.4.2 系統狀態機

### 5.1 大同智能的設計

大同將系統拆成六個主要模式：

- M1 併聯：市電正常，PV 自用，ESS 削峰或充電，DG 停機。
- M2 切換中：市電異常持續 T1 後，ATS 切到自主側並啟動 ESS GFM。
- M3 孤島 ESS：ESS 建立電壓／頻率，PV 視條件併入。
- M4 孤島 DG＋ESS：SOC 低於 20%，由 DG 建壓供電，ESS 轉 GFL 充電。
- M5 DG 單獨：ESS 故障時，由 DG 支撐關鍵負載。
- M6 回切中：市電恢復持續 T2 後，停止孤島電源並切回市電。

參數表還給出 SOC 20%／80%、10%／95% 極限、並聯 reserve 50%、T1/T2 60 秒、DG 暖機 30–60 秒、冷卻 60–120 秒。這些數字讓狀態圖不只是概念，而開始具備可實作參數。

### 5.2 強項與工程努力

- **把多設備協同形式化。** 大同沒有只寫「停電時啟動備援」，而是畫出來源切換、ESS 模式變更、DG 充電與市電回復。
- **有失敗分支。** ESS 故障時另設 M5，而不是假設 ESS 永遠健康。
- **有時間確認。** T1/T2、暖機與冷卻避免瞬時擾動造成頻繁啟停。
- **有 SOC hysteresis。** 20% 啟動 DG、80% 停止 DG，避免單點門檻來回震盪。
- **採全黑切換是可理解的保守選擇。** 對小型場域而言，它可降低來源重疊與同步併聯複雜度；這是成本、安全與可維護性的取捨，不應只視為缺點。

### 5.3 需要和大同討論

- M2、M4、M6 的實體 breaker／ATS 順序、dead-bus、live-bus 與 feedback gate 尚未寫完整。
- 「全黑切換」與「同步併聯盤」混用，需確認真正採 open-transition 或 closed-transition。
- ESS GFM、DG forming 與 ESS GFL 同 bus 時，誰是 reference source、誰驗證同步接受？
- Windows EMS 若離線，狀態機是否仍由本地 PLC／控制器繼續？
- 每條 transition 需補 trigger、permissive、command、ack、feedback、timeout、retry、fallback 與人工復歸。

## 6. 2.5.1 EMS 調度策略

### 6.1 大同智能的策略

核心原則是：

> ESS 優先供電 → SOC 不足時 DG 輔助並為 ESS 充電 → SOC 回升後再由 ESS 接手。

日間由 PV 優先供負載，餘電充 ESS；PV 不足時 ESS 補缺口。夜間由 ESS GFM 供電。SOC 低於 20% 時，先全黑切換，由 DG 建立 V/f，再讓 ESS 以 GFL 充電；SOC 高於 80% 後停止充電、DG 冷卻停機，再切回 ESS GFM。

方案也提出 DG 燃油時數、剩餘油量估算與非關鍵負載卸載。

### 6.2 強項與工程努力

- **調度目標很清楚：少燒油、保供電。**
- **把 DG 當作能量補充設備，而不是長時間主供。** 這可避免 DG 全天低效率運轉。
- **把 ESS 的成網與充電角色分開。** GFM／GFL 轉換顯示大同理解微電網中的 reference source 問題。
- **同時考慮供給側與需求側。** 除 PV、ESS、DG 外，還納入 load shedding。
- **有燃油管理概念。** 提案不是只看 SOC，也開始納入災時後勤限制。

### 6.3 需要深化

固定 20%／80% 適合作為第一版規則，但正式調度還要加入：

- 未來數小時的負載與 PV 預測。
- DG minimum run time、minimum off time 與最低負載率。
- ESS EOL usable energy、溫度與 BMS CCL/DCL。
- 啟動失敗、低油量、PV 預測誤差與負載突增。
- no-break／critical／deferrable 負載優先順序。

## 7. 72 小時自主供電與負載管理時序

### 7.1 大同智能呈現的時序

範例以 3 kW 平均負載、白天約 8 小時 PV、夜間 ESS 放電與 DG 補電來示範：

1. Day 1 白天：PV 供載兼充電，SOC 約 50%→95%。
2. Night 1 前段：ESS 放電，SOC 約 95%→20%。
3. Night 1 DG 充電：約 3 小時，DG 供載並把 ESS 充至 80%。
4. Night 1 後段：切回 ESS，SOC 約 80%→70%。
5. Day 2：PV 再充至約 95%。
6. Night 2、Night 3：ESS 與 DG 依 20%／80% 門檻循環。
7. 72 小時估計全黑切換 6–10 次，DG 累積運轉約 6–10 小時。

### 7.2 這張圖的重要價值

這是整份提案最值得肯定的部分之一。大同沒有只寫「可以撐 72 小時」，而是嘗試把：

- 白天與夜間。
- SOC 變化。
- PV、ESS、DG 各自的工作區段。
- 柴油機啟停次數。
- 全黑切換次數。

放到同一個時軸。這顯示供應商確實做過 operational scenario thinking，也讓後續 FAT/SAT 有了可以轉成測試腳本的基礎。

### 7.3 尚不能直接證明 72 小時的原因

- 37 kWh/day 相當於 1.54 kW 平均；範例使用 3 kW，兩者不一致。
- 30 kWp×3.5 h/day 是毛發電估算，尚未扣除 PR、陰雨、遮蔭與孤島 curtailment。
- ESS 有 58/60 kWh 兩個版本，usable energy、EOL 與轉換效率未寫。
- DG 有 13–15 kW、20 kW、30 kVA 三種表達。
- 油箱有 400 L、500 L 兩個版本。
- 6–10 次、每次最多 5 分鐘全黑，累積可能中斷 30–50 分鐘。

正確的下一步不是否定這張圖，而是請大同提供原始 15 分鐘／1 小時模型、負載清單、PV 情境、設備效率與燃油曲線，把這個很好的概念圖升級為可驗證計算書。

## 8. 3.1 通訊拓樸架構

### 8.1 大同智能的架構

- EMS 主機透過 LAN switch 連接現場設備。
- ET-7044 I/O 模組以乾接點操作 EMP Panel ATS／DG。
- GW-2235i 做 Modbus RTU↔TCP 轉換，透過 RS-485 收集 PCS、BMS、PV、DG。
- FortiGate 提供 NAT／ACL／VPN 邊界。
- ADSL 作為唯一外網通道。
- UPS 為 EMS 與網路設備提供至少 30 分鐘備援。
- 北向預留 DNP3 over TCP/IP，EMS 作 Outstation，未來可接 SCADA Master。
- 現場採有線 Ethernet／RS-485，降低無線干擾與攻擊面。

### 8.2 強項與工程努力

- **現場與上位分層清楚。** Modbus 適合現場整合，DNP3 適合未來 SCADA。
- **同時設計控制與資料採集。** 控制模組週期 ≤5 秒，資料採集模組 30 秒。
- **有 protocol conversion 與實際 I/O 型號。** 表示方案已接近採購與盤體設計。
- **有基本資安邊界。** Firewall、VPN/HTTPS、ACL、帳號權限、登入記錄與六個月日誌都有被考慮。
- **有控制電源續航。** UPS 顯示大同注意到 EMS 本身也需要被保護。

### 8.3 需要深化

- 關鍵 ATS、DG start/stop、EPO 不應只依賴 Ethernet 或 Windows EMS。
- 控制週期 ≤5 秒與採集 30 秒的資料依賴關係需釐清。
- Modbus register map 要補 unit、scaling、quality、stale、heartbeat、ack、timeout 與版本。
- DNP3 Secure Authentication v5 目前標示「預留」，不能視為已實作。
- 需要 OT VLAN／zone、憑證、MFA、備份還原、patch、allowlist 與遠端操作雙重確認。
- ADSL 失效時，本地狀態機與操作必須完全可用。

## 9. 5.1.1 併聯／孤島切換方案

大同定義的流程是：偵測市電異常 → 持續確認 60 秒 → ATS 切至自主側 → DI 回讀 → PCS 全黑啟動 GFM → 建立 110/220 V 微電網 → PV 偵測後併入。

回切則是：市電恢復 → 持續穩定 60 秒 → 若 DG 運轉先冷卻停止 → PCS 停止輸出 → ATS 切回台電 → DI 回讀 → PCS/PV 恢復併網。

強項：

- 有 command＋DI feedback，而不是只發命令。
- 異常恢復後不立即回切，避免市電抖動。
- DG cooldown 被放進 sequence。
- PV 是在微電網建立後才考慮併入，順序合理。
- 用全黑避免來源重疊，是可理解的第一版設計。

需要討論：

- 60 秒是市電異常確認時間還是保護動作後的等待？緊急避難負載能否接受？
- PCS 建 V/f 前須證實 PCC open、bus dead、BMS ready、PCS GFM available。
- PV 是否真的支援由 ESS 形成的孤島 bus。
- ATS timeout、stuck、回讀矛盾與 unknown state 要有 fault lockout。
- Life-safety 與 no-break 負載不能跟著全場等待切換。

## 10. 5.2.1 ESS↔DG 解決方案

### ESS→DG

大同流程為：SOC 到 20% → PCS 停止 GFM、系統全黑 → 乾接點啟動 DG → DG 暖機並建立 V/f → 同步盤投入 → PCS 切 GFL 充電。

### DG→ESS

SOC 到 80% → PCS 停止充電 → 同步盤斷開 → DG 無載冷卻 → 停止 DG → PCS 全黑啟動 GFM → PV 自動併入。

強項：

- 把 DG 暖機、無載冷卻寫進控制邏輯。
- 充電功率與負載供電有同時考慮。
- 有 DG 遠端監控、狀態與剩餘油量估算。
- 有 ESS 故障時 DG-only 的降級模式。
- 400 L 油箱在 50%／75%／100% 負載下做了支撐時數估算。

需要討論：

- 若採全黑 open-transition，文件中的「同步併聯」名稱需調整。
- 若 DG bus 已 live，ESS GFL 併入必須由 PCS 自行完成同步接受。
- 充電 setpoint 上限應為 BMS CCL、PCS limit、DG headroom 與 minimum load 的共同結果。
- DG 啟動失敗、重試上限、低油量與過載後 fallback 未完整。
- 400/500 L 與 13/15/20 kW 需要統一。

## 11. 5.3.1 併聯模式解決方案

大同在市電正常時提出：

- PV 發電大於負載：ESS 充電吸收餘電，SOC 到 95% 停止充電。
- PV 小於負載且 SOC 大於 50%：ESS 放電補缺口。
- SOC 小於等於 50%：停止放電，由市電補足。
- 平時保持 SOC 50%–95%，保留防災隨時待命能力。

這個設計的優點是把經濟運轉和災害備援結合。大同不是追求每天把電池循環到最低，而是保留至少 50% 防災 reserve。對公部門避難設施而言，這個服務導向比單純電價套利更合理。

需要補充的是：50% reserve 應由天候、颱風警報、預估停電風險、EOL 容量及關鍵負載 horizon 動態調整，不一定全年固定。

## 12. 5.5.2 日前排程與動態調度

大同設計每天 23:00 觸發排程，引擎輸入：

- PV 發電預測。
- 歷史負載曲線。
- ESS SOC／SOH。
- DG 剩餘油量。

輸出下一日 24 時段的充放電功率、SOC 預估、DG 啟動時段與告警。系統每 15 分鐘比較實際與預測，偏差超過門檻時重排後續時段。

### 這一節的強項

- **從規則控制走向預測控制。**
- **日前＋即時修正的兩層時間尺度合理。**
- **把 SOH 與燃油納入，不只看當下 SOC。**
- **並聯與防災模式使用不同目標。**
- **對小型場域採移動平均與天氣分類，是務實而可維護的第一版。**

這顯示大同不只是做 SCADA 畫面，而是嘗試建立真正的 EMS scheduling engine。

### 需要討論

- 目標函數是最低電費、最低油耗、最高韌性，還是多目標加權？
- 15 分鐘粒度是否能捕捉 motor start 與突發負載？
- PV 預測低於預估 70% 才重排的門檻如何決定？
- 排程不可覆蓋 BMS CCL/DCL、PCS limit、DG minimum time 與 L1 interlock。
- 需要保存 forecast version、input quality、schedule version、manual override 與實際偏差。

## 13. 其他值得肯定的工作

### 13.1 異常處理

方案已列出：

- ATS command／DI 不一致：重試一次，仍失敗則鎖定。
- 孤島 ESS 通訊中斷：維持最後狀態 60 秒，再啟動 DG。
- DG 通訊中斷：保持模式、告警、禁止新啟動。
- SOC 到 10%：強制停止放電。
- PV inverter 故障：以 ESS／DG 補缺口。
- 所有電源失效：告警並執行負載停電。

這些內容證明大同已思考 fault response，而不只是正常流程。

### 13.2 HMI 與操作

七個頁面涵蓋總覽、單線圖、排程／模式、ESS、告警、報表與權限；管理員與一般使用者分權，支援桌機、平板、手機。對場域維運而言，這是一個完整而實用的初版資訊架構。

### 13.3 DNP3

將 EMS 設為 DNP3 Outstation，預留未來由 SCADA Master 輪詢與控制，並定義 Class 0/1/2/3 點位方向，顯示供應商有考慮公用事業／上位調度整合，而不是把系統做成封閉孤島。

### 13.4 FAT／SAT

FAT 包含 Modbus、DNP3、斷線、24 小時穩定性及 HMI；SAT 包含實機通訊、ESS 能量、效率、切換、72 小時運轉與操作畫面。

最重要的意義是：大同已經把交付想成「需要被驗證的系統」，不是設備到場通電就結案。雖然 pass/fail 條件還需量化，驗證骨架本身值得保留。

## 14. 大同智能方案的主要強項

### 14.1 系統整合完整

同一提案把能源、控制、通訊、資安、操作與測試串在一起。這是總包型供應商最重要的能力。

### 14.2 現場導向

使用乾接點、DI 回讀、RS-485 gateway、商用 firewall、UPS 與 Web HMI，反映方案考慮既有設備與維護人員，不是純軟體架構。

### 14.3 模式與時序有被具體化

M1–M6、T1/T2、SOC 20/80、暖機／冷卻、72 小時時序，使各方可以指著同一張圖討論。

### 14.4 防災目標優先於套利

平時維持 50% reserve，災時 ESS 優先、DG 補充、PV 續航，符合避難設施的價值排序。

### 14.5 有產品化思維

參數可由 EMS 介面調整、HMI 有固定頁面、北向預留 DNP3、報表可匯出、帳號有分級，顯示不只是一次性盤控。

### 14.6 有測試與驗收意識

從 HIL、FAT 到 SAT、72 小時實測，已開始建立完整交付生命週期。

## 17. 建議下一輪與大同智能的討論方式

不要一開始質問「為什麼數字不一致」，而應先確認大同已完成的設計，再要求升級證據：

1. 請大同先用原圖逐一說明 M1–M6 的實體電力路徑。
2. 共同確認第一版是否明確採 open-transition。
3. 請提供權威 SLD、breaker／ATS ownership 與 interlock matrix。
4. 請提供 72 小時原始時序模型、critical-load 清單與最壞天候情境。
5. 凍結 ESS、PCS、DG、油箱的正式規格版本。
6. 確認狀態機是跑在 EMS Windows 主機、PLC、PCS controller 或其他本地控制器。
7. 逐條確認 PV island support、DG forming、ESS GFM/GFL 的設備證據。
8. 將 FAT/SAT 改寫成有刺激、時間、容許值、trace 與 pass/fail 的 DVP&R。

這樣的討論方式既承認供應商投入，也能把概念設計推進到可簽核的詳細設計。

## 18. 對本專案的適用結論

大同智能方案最值得借鏡的不是 58/60 kWh 或 20/80% 等數字，而是：

- 用狀態機管理市電、ESS、DG、PV。
- 把 72 小時供電變成時序情境。
- 把能源調度、現場通訊、HMI 與 FAT/SAT 串在一起。
- 用 reserve、燃油與負載管理平衡韌性與成本。
- 讓操作人員看到模式、告警、趨勢與排程。

如果要移植到 100 kWh 自研 BMS＋EMS，應保留大同的 use-case 與操作經驗，但採用：

- L0：BMS／PCS／DG／relay 本地保護。
- L1：deterministic microgrid PLC/controller。
- L2：EMS optimizer／command orchestrator。
- L3：Web HMI／SCADA。

大同的方案可以是很好的場域與操作需求來源；自研案仍需自行完成 cell limits、BMS safety、PCS operating envelope、AC protection、接地、SLD、ICD 與驗證證據。

## 19. 建議和使用者優先討論的五個決策

1. 你希望評估的是「大同這個案子做得多完整」，還是「我們是否要採用大同作法」？兩者結論不同。
2. 五分鐘全黑對這個避難場域是否可接受？哪些負載必須不斷電？
3. 你傾向保留大同的簡單 open-transition，還是要投資 closed-transition／更短切換？
4. EMS 是否只做上位監督，另設 PLC；還是大同已有未拍到的本地控制器？
5. 下一輪要先向大同索取哪一份證據：權威 SLD、72 小時計算書、設備 datasheet、state table，或 FAT/SAT 詳規？

這五題會決定後續是「採購澄清」、「共同設計」，還是「自研架構吸收」。
